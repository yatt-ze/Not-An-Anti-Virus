**Changelog from v0.14:** Documentation-only restructure — no design, architecture, scope, or phase change. The single `docs/design.md` was split into an index (`docs/design.md`, keeping the front matter and §1–§3) plus topic files under `docs/design/` — `scanner.md` (§5–§8), `platform.md` (§4, §9), `gaps-and-requirements.md` (§10–§11), `roadmap.md` (§12–§14) — and this changelog moved out to `docs/design-changelog.md`. Section numbers are unchanged and remain global: `§11.9` means what it did before and is still the form to cite in code comments and commit messages. Prompted by the changelog block having grown to roughly a fifth of the file while never being cross-referenced by number, and by §5–§8 (active Phase 0a work) and §4/§9/§10/§11 (Phase 0b+ feasibility material) changing at very different rates.

**Changelog from v0.13:** The `.pkg` parsing from v0.13 is now wired to verdicts, via two rules kept deliberately separate because they are different kinds of evidence: `installer-script-suspicious` (`StaticSuspicion`) scores what a package's install scripts contain, and `unsigned-installer-package` (`ProvenanceConcern`) notes a container carrying no signature. Splitting them is what lets a package that is both unsigned *and* fetches remote code in a preinstall corroborate across two categories under §5.1, instead of one rule inventing a large weight alone. **The script rule adds no heuristics of its own** — it reaches the script text through the TOC, heap, gzip and cpio, then hands those bytes to the existing content rules, so what the container work buys is *reach*, not a new detection, and the scoring rides on rules the corpus has already exercised. Enabling that needed one reshape: `ScanContext::from_embedded_bytes`/`scan_embedded_bytes` let the engine score bytes that were never a file, since Phase 0a extracts nothing to disk. A label is not a path, so a new `ContentSource` marks container-extracted content and the three rules that read meaning into `ctx.path` (signing, quarantine xattr, launchd location heuristics) report `NotApplicable` for it rather than drawing conclusions from a name this crate invented — which also means a container member can never come back as a `Complete` clean scan, the honest outcome under §10/§11.8. Separately, a false positive was found and fixed in `unsigned-binary`: it treated `codesign -dv`'s "code object is not signed at all" as proof of an unsigned binary, but that is what codesign says about *anything* it doesn't recognize, so the rule had been firing on every plain text file, tarball and script scanned (confirmed: `readme.txt` scored 4 on it). It now checks for Mach-O magic first. New fixtures: three benign packages (ordinary scripts, no scripts, and a nested `productbuild` container) all scoring 6 → no action, and one suspicious package scoring 15 → notify. No architecture/phase/scope change — Phase 0a scanner work per §12.

**Changelog from v0.12:** `.pkg`/xar container parsing landed, closing §12's "biggest untouched parser surface" for Phase 0a. Three bounded, hand-written readers under the §3 no-third-party-code-on-the-parse-path rule: `nav_core::inflate` (already in v0.12) gained a gzip/RFC 1952 wrapper, `nav_core::cpio` reads odc and newc archives, and `nav_core::xar` reads the container header, the zlib TOC, and the TOC's XML tree. Together they reach what §5.2 and §6.1 actually ask for — package structure, signature block, and install-script *contents* — while leaving `Payload` alone, since payload inspection stays behind §6.2's explicit-command scratch path in Phase 0b. Three format details were confirmed against real `pkgbuild`/`productbuild` output rather than assumed, each of which breaks a reasonable-looking implementation: install scripts are **not in the TOC** (they are a gzip stream wrapping an odc cpio archive in the heap, so reading them needs all three readers); a `<file>`'s `<name>` can appear **after** its nested children in the raw bytes, so paths are resolved in a second pass (`xar --dump-toc` reorders fields and hides this); and the TOC's `encoding` attribute is **backwards** — entries labelled `application/x-gzip` are zlib, while the `Scripts` entry labelled `application/octet-stream` is genuinely gzip — so entries are dispatched on their leading bytes, never the label. The TOC is a tree, not a list: a nested `.pkg` appears as a `<file type="directory">` with children, which is where §6.2's recursion-depth ceiling (default 4) now applies. A container declaring an unsupported xar version halts rather than being parsed as version 1, since guessing the layout would mean reporting confident results about a misread file. Consistent with §10/§11.8 throughout, a damaged container yields the entries recovered plus an explicit halt reason rather than an error or a clean-looking empty result, and an entry whose heap location falls outside a bounded read reports as unreachable rather than absent. The XML itself is read through a new `nav_core::xml` module — one bounded XML implementation shared with the plist reader, rather than a second one alongside it, since two would mean two things to fuzz under §11.9 and two places for the same edge case to go wrong differently. That consolidation was not cosmetic: bringing the two together surfaced two defects in the newer reader that the older one did not have — it stepped through text a byte at a time and pushed `char::from(b)`, corrupting any non-ASCII name or attribute (`café` → `cafÃ©`), and it skipped comments and processing instructions by recursing, so a document with a long run of them consumed a stack frame per comment. The shared module keeps the correct behaviour in both cases and pins each with a test. Three new `cargo-fuzz` targets (`inflate`, `parse_cpio`, `parse_xar`) join the Mach-O and plist ones, each asserting its own §11.9 materialized-byte ceiling rather than only checking for panics — the xar target also asserts the §6.2 entry-count and recursion-depth ceilings on what comes back, and exercises `read_entry` on every entry a TOC describes, since that is where a few bytes of container try to become a large allocation. All five targets were run against corpora seeded from `testdata/` (~94M total executions) with no crash, timeout or OOM; that partially closes §12's "run the fuzz targets on a nightly box" item, though sustained runs still belong in CI rather than ad hoc on a laptop. No architecture/phase/scope change — Phase 0a scanner work per §12.

**Changelog from v0.11:** `nav-core` gained a bounded DEFLATE/zlib decoder (`nav_core::inflate` — RFC 1951 and RFC 1950), the first piece of the `.pkg`/xar work §12 lists as Phase 0a's remaining parser surface: a xar stores its table of contents — the file table, the signature block, and the heap pointers to the install scripts — as a zlib stream immediately after a 28-byte header, so none of that metadata is reachable without inflating first. Hand-written rather than taken from a compression crate, and §3 now states the rule that decision follows from: **no third-party code on the attacker-controlled-input path**. That is deliberately narrower than "no dependencies" (`serde`, `clap` and peers are fine, and `nav-core` already links several) and stronger than "few" — what it protects is the panic contract. These parsers must return `Err` on hostile input, a foreign decoder can only promise that by convention, and under a root daemon (Phase 0b+) a panic reachable from a malformed `.pkg` is a denial of service. The decoder carries §3's output-budget discipline natively: the budget is checked *before* every write rather than after, so a bomb is refused rather than materialized and then rejected, and `BudgetExceeded` is kept distinct from `Malformed` because hitting a limit is §6.2's `scan-halted: extraction-limit-exceeded`, which explicitly does not imply the container is malicious — legitimate installers are large. Differential-tested against CPython's zlib over a committed vector corpus (`testdata/inflate/`, with the generator that produces it) covering all three block types, back-references at the 32 KiB maximum distance, incompressible data and an 840:1 bomb, plus truncate-at-every-prefix and bit-flip sweeps that assert no input can panic the decoder or make a partial decode look complete. No architecture/phase/scope change — Phase 0a scanner work per §12.

**Changelog from v0.10:** `nav-core` gained a small, bounded, dependency-free property-list reader (`nav_core::plist` — binary `bplist00` and the XML subset) parsed under the §3/§11.9 discipline: no panics, every offset bounds-checked, hard depth/node ceilings, reference-cycle detection on the binary object graph, and a `cargo-fuzz` target alongside the Mach-O one. Review of that reader turned up two amplification defects — distinct from the bounds checking, which held: every individual read was in range, but nothing bounded the *total* output. In the XML path an unrecognized entity left the cursor un-advanced, so each `&` re-scanned and re-appended the rest of the text (a 64 KiB file drove `navctl scan` to 1.08 GB RSS); in the binary path, objects shared by reference form a DAG that the cycle guard correctly permits but that `decode` re-materialized per path (an 8 KB file decoded to 82 MB). Both are fixed — a bounded entity lookahead, and a parse-wide `MAX_TOTAL_BYTES` budget — and the lesson is recorded as a standing rule in §3: a node/depth ceiling is not a memory ceiling once inputs can share structure, and neither shape is reachable by mutating a valid-plist seed, so the fuzz target now asserts a materialized-byte ceiling too. `.app` main-executable resolution (§5.8) now consults the authoritative `Contents/Info.plist` `CFBundleExecutable` key via that reader, falling back to the `Contents/MacOS/<name>` naming convention when the plist is missing/unreadable/malformed/keyless; the value is reduced to its final path component so a hostile key can't redirect resolution outside the bundle. Closes the tracked v0.9 follow-up (issue #6); new benign `NamedDiff.app` fixture (binary `Info.plist`, executable name ≠ bundle name). The same reader backs a new static rule, `launchd-persistence-plist` (§5.2, `BehavioralConcern`): it recognizes a launchd job plist and scores only anomalies — `RunAtLoad`+`KeepAlive`, a program path in a transient/hidden location, an inline `sh -c`/`osascript -e` loader, a sub-5-minute `StartInterval`, or the plist staged inside an `.app` bundle / on a mounted volume — nothing for a well-formed ordinary LaunchAgent (§1). Purely static: no process-attribution claim (that stays §5.3). Both location heuristics carry carve-outs found in review, each of which had been flagging a whole class of ordinary software at `notify`: an app's own `Contents/Library/Launch{Agents,Daemons}/` helper is at its documented installed location, not staged, and a hidden program directory directly under a home directory that is a known per-user tool root (`~/.local`, `~/.cargo`, …) is not an unusual location. New `benign/com.example.helper.plist`, `benign/com.example.devtool.plist`, a bundled privileged helper inside `benign/SampleHelper.app`, and `suspicious/com.apple.softwareupdate.plist` (binary) fixtures. No architecture/phase/scope change — Phase 0a scanner work per §12.

**Changelog from v0.9:** Added `.app` bundle awareness for on-demand scans (§5.8, new). `navctl scan` and `navctl rules test` now resolve a target — file, directory, or `.app` bundle — through one shared resolver in `nav-core` (`scan_target`), fixing a divergence where `rules test` on a directory/bundle scanned the directory inode itself: the read failed, every rule reported `NotApplicable`, and the all-`NotApplicable` scan rendered as "no action (clean)" — a "couldn't check" folded into "checked and clean", exactly what §10/§11.8 forbid. A `.app` bundle is scanned as one unit: every member is traversed regardless of `--recursive` (a bundle is inherently nested, and trojanized `.app`s hide payloads in `Contents/Resources/` or helper tools, not just the main binary), the main executable is resolved by the `Contents/MacOS/<name>` convention (authoritative `Info.plist`/`CFBundleExecutable` parsing is a tracked follow-up — real bundles ship binary plists, needing the §11.9 parser discipline), and a narrow fixed set of compiled resources (`Info.plist`, `PkgInfo`, `_CodeSignature/`, `.nib`/`.car`/`.strings`/`.lproj`/…) is traversed but not scored, to limit false-positive surface (§1). A directory/bundle verdict is the worst single member's — per-file scores are never summed. `rules test` gains `--recursive` to mirror `scan`. The shared walker also sorts output (§11.1) and no longer follows directory symlinks. New benign `SampleHelper.app` fixture pins this in the FP harness, which now also walks `.app` directory fixtures. No architecture/phase/scope change — Phase 0a scanner work per §12.

**Changelog from v0.8:** Implemented Phase 0a's Mach-O `__TEXT` entropy heuristic (§5.2). `nav-core` now carries a small, bounded, dependency-free Mach-O parser (thin and fat/universal) that locates the `__TEXT,__text` section, and the entropy rule scores *structurally* rather than whole-file: high entropy is a suspicion signal only inside a Mach-O `__TEXT` section (packed/obfuscated code) or embedded in a script/text file (obfuscated/base64 payload). On an opaque non-Mach-O binary — a compressed archive, an image, encrypted data — high entropy is expected and is no longer scored at all, removing a whole-file-entropy false positive that conflicted with the §1 low-false-positive-rate priority. No architecture/scope/phasing change — this is Phase 0a scanner work per §12, and the parser is deliberately narrow (locate `__TEXT`, nothing more) with a `cargo-fuzz` target as its planned next step.

**Changelog from v0.7:** Fixed a real architectural inconsistency: §2 previously said the privileged daemon hosts "all monitoring + scoring logic," which would mean Phase 0a's "no daemon required" claim was false — any on-demand `navctl scan` would have needed `navd` running just to reach the engine. Resolved by extracting the heuristics/scoring engine into its own crate, `nav-core` (§3), linked directly by both `navctl` and `navd`. `navctl` now runs on-demand scans in-process against `nav-core`, with no daemon, socket, or privilege involved; `navd` links the same engine for anything that genuinely needs privilege (automatic write-time scanning, FDA-gated paths, the full event/correlation/notification pipeline). Clarified in §9.1 that the socket is for daemon-owned state only, not a dependency for scanning.

**Changelog from v0.6:** Fixed §5.4's stale `ProcessAttribution` reference (again — confirmed no further instances). Reframed the FDA check from a single "granted/not-granted" canary to a per-area coverage-probe matrix (`ProtectedCoverageArea`/`CoverageProbeResult`), since Apple provides no reliable API to determine FDA status and a single probe overclaims certainty. Flagged an active, unresolved macOS Tahoe 26.1/26.2-beta bug (Trellix-reported, Apple DTS-engaged) where CLI binaries fail to appear in the FDA list at all — an immediate platform risk, not just a design-time hypothetical. Softened the FDA-durability claim in §11.10 from asserted to expected-but-must-be-tested, with a concrete upgrade-scenario test matrix. Relaxed `navnotify`'s locked constraint from "no app bundle" to "no conventional application" — a minimal agent-style `.app` with no Dock presence satisfies the same requirement, and which form it takes is now an explicit Phase 0b question. Corrected the notification-action attack-surface claim and added an opaque `finding_id`+nonce request model instead of raw paths. Replaced overclaiming exit codes (clean/malicious) with confidence-appropriate ones that distinguish complete from partial/indeterminate scans. Rewrote the canonical `rules test` example to show score/confidence/completeness/attribution together, and renamed the "known-good-parent" signal to "interactive-user-launch" with informational-only weight. Converted §11 from a flat numbered list to titled subsections (§11.1–§11.11). Split Phase 0 into three sequenced sub-phases (0a: scanner validation, needs no daemon/root/FDA; 0b: platform integration feasibility; 0c: behavioral/network sensor feasibility) so the highest-value, lowest-risk question — does the scanner produce useful verdicts? — gets answered before deeper platform investment, without renumbering Phases 1–4.

**Changelog from v0.5:** Designed a concrete FDA solution: `navctl setup fda` as an explicitly user-invoked command, never triggered automatically by install or any other command, consistent with the non-invasive philosophy. Added self-diagnosis (canary read at startup, surfaced in `navctl status`) and per-event visible "not scanned" markers so FDA-related coverage gaps are never silent. Tied the Homebrew safe-install path (§11.10) to FDA-grant durability across upgrades. Added the `navd`-vs-`navctl` TCC-exposure distinction and system-vs-per-user grant scope as explicit Phase 0 spikes.

**Changelog from v0.4:** Fixed `§5.4`'s stale reference to old `ProcessAttribution` variant names (`Pid`/`Inferred`) that no longer match the enum defined in §4.1. Added Full Disk Access / TCC as an explicit honest gap and Phase 0 feasibility spike — root does not bypass TCC for user-data folders, and NAV has no app bundle to drive a consent flow, so static-analysis coverage of Downloads/Desktop/Documents needs empirical verification, not assumption. Added ruleset/config integrity as a cross-cutting requirement (§11.11) — a tampering-detection tool needs its own files protected against the same tampering. Added a notarization requirement to the distribution decision in §13. Made the self-defense-vs-infostealer tradeoff in §10 explicit rather than implied. Added a `notify delivery: ok/degraded/disabled` health indicator to `navctl status` so notification-delivery failures are discoverable, not silent.
