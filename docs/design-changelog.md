**Changelog from v0.41 (2026-09-29):** Fixed `macho-loader-anomaly` reading a signature it could not parse as "signed, no entitlements" (§10/§11.8, #55). When a slice's `LC_CODE_SIGNATURE` region was read but its SuperBlob had a bad magic or more than 256 blobs, both parse paths (`scan_ranged` and `parse`) fell back to default facts and marked the region `Read`, so the rule reported clean. A new `SignatureRegion::Malformed` marks that case as undetermined: `macho-loader-anomaly` returns `NotApplicable` for the entitlements half and the scan is `Partial`. No fixture for that fix, since the outcome is `NotApplicable`/`Partial` and not a signal. `unsigned-installer-package` now counts only a `<toc>`-level `<signature>` with an `offset` and non-zero `size` inside the archive as signed; a nested, bare or out-of-range one is treated as unsigned (§5.2, #40). The xar walk also never stored the signature it found in `XarArchive.signature`, so every package fired the rule; that is fixed. New fixture `suspicious/installer_spoofed_signature.pkg`; the golden snapshot gains that one entry. `--json` no longer panics on a non-UTF-8 path (Linux): `ScanResult.path` and the `navctl` multi-target envelope's path fields serialize lossily (U+FFFD) through `model::lossy_path`, `with_schema_version` and `scan_result_json` return `Result`, and a failure exits `4` (§8, #44). No `schema_version` bump. `high-entropy-content`'s base64 carrier detection was quadratic on a long single-line script (every identifier-like run rescanned back to the previous newline), so a minified 14 MB JS bundle never finished scanning. Detection now runs once per run and only when a candidate passes the length check, and `find_pem_carrier` looks back at most 1024 bytes per line (§5.2, #59). PR #60 review: an unwalkable SuperBlob index (header or declared index past the region, an entry pointing outside it) is also `Malformed`; only the root `<toc>`'s first `<signature>` is recorded, and a range past a truncated embedded capture is `NotApplicable`; the PEM line cap is inclusive of 1024 bytes; lossy JSON paths can collide.

**Changelog from v0.40 (2026-09-27):** Began fixing #45: every file over the 8 MiB read cap (§3) was `Partial`, so 12 of 26 real app main executables could never scan `Complete`, even notarized and clean. §5.5's truncation rule is now a central default with a per-rule opt-out. `Rule::covers_truncation(ctx)` (default `false`) lets a rule declare that its result for this file doesn't depend on bytes past the prefix. A truncated file stays `Partial` unless every rule that ran declares it. `ScanContext` keeps the handle the prefix was read through and gains `read_at` (≤ 16 MiB per call) and `for_each_window` (1 MiB chunks, ≤ 512 MiB per call), so a rule can read past the prefix without reopening the file by path (§11.7). No rule opts in yet, so behaviour is unchanged by this step.

Rest of #45, no further version bump: the codesign rules, `quarantine-xattr-present`, `launchd-persistence-plist` (when the content can't be a plist) and the package rules (when it isn't xar) opt in without reading further. `suspicious-strings` streams the whole file; a bounded marker ending a non-final window waits for the byte that follows it. `high-entropy-content` streams a Mach-O's whole `__TEXT,__text` into a byte histogram. `macho-loader-anomaly` now parses every slice by offset (`macho::scan_ranged`, memoized per scan): header plus the full declared load commands (≤ 2 MiB), then the `LC_CODE_SIGNATURE` region (≤ 16 MiB), ≤ 64 MiB of ranged reads per file. "Couldn't determine entitlements" now means the signature region wasn't read, not that the file was truncated. It opts in only when every slice and signature was read. The §11.12 byte budget counts each file up to the 512 MiB streaming cap instead of the 8 MiB prefix. Real-corpus comparison of every file over 8 MiB under `/Applications`, the Homebrew Cellar, `~/.cargo/bin` and `/usr/bin` (322 files; smaller files take the same path as before): `Complete` went from 0 to 306. `.tbd` text stubs, `.pkg` archives and files over the stream cap stay `Partial`. Recommendations changed for 8 files. One `notify` became `no-action`: openblas, whose whole `__text` measures lower entropy than its prefix did. Seven became `notify`, all from `suspicious-strings` markers that were always present but past the prefix: GarageBand, Xcode's LLDB and IDEFoundation frameworks and its `CodeResources`, two ProtonVPN system extensions, and ZAP's bundled `libjvm`. These are the rule's existing noise on large benign binaries now made visible, not a new detection bug; weighting is #35/#48's concern. RawTherapee now scores +10 for a genuine `allow-dyld-environment-variables` entitlement whose signature previously lay past the prefix. Still `Partial`: files over 512 MiB, `.pkg` archives and scripts over 8 MiB. No fixture over 8 MiB can be committed, so coverage is generated-file tests. Golden snapshot unchanged. The §5.5 contract now says what the code does: a rule whose streamed read fails either returns `NotApplicable` or keeps its finding and records the failure so `covers_truncation` (called after `evaluate`) returns `false`. `high-entropy-content` scores `__TEXT` ranges under one 512 MiB budget; a range the budget leaves out now makes the rule `NotApplicable` (so the scan is `Partial`) unless another slice already matched, in truncated and non-truncated files alike (#56).

**Changelog from v0.39 (2026-09-27):** Reordered the §8 exit codes so a finding outranks incompleteness (#34). `for_target` took the numeric max of per-file codes, and `INDETERMINATE` (3) > `HIGH_RISK` (2), so one ordinary file over the 8 MiB read cap (§3) in a directory turned a high-risk scan's exit `2` into `3`. Almost every real directory has such a file, so a script checking for `2` would effectively never see it from a directory scan. Now `for_result` maps `Notify`/`NotifyAndSuggestQuarantine` to `1`/`2` whatever the completeness, and only a `NoAction` result short of `Complete` maps to `3`. `for_target` aggregates in severity order `2` > `1` > `3` > `0`, and incomplete coverage (budget, unreadable subdirectory) raises only a clean target to `3`. Content past a read boundary can only add weight: the only negative-weight rule (`notarized-binary`, −3) is path-based. But `Partial` also comes from a rule returning `NotApplicable`, which includes `notarized-binary` itself. So a partial score can overstate by up to 3, erring toward alerting and never toward a false clean. The invariant that an incomplete scan never returns `0` is unchanged. The cost: `1`/`2` no longer carry completeness. Per-file `completeness` is in `--json`; target-level coverage for `navctl scan --json`/`navd scan-once --json` is stderr-only (#51). §5.5 now says the exit code is a report and `is_actionable()` (NAV-005) still gates automatic action. §8, §11.12 and the README exit-code table are updated to match. Constant values, `--json` shape and `SCAN_JSON_SCHEMA_VERSION` are unchanged; no scoring change.

**Changelog from v0.38 (2026-09-27):** Made `high-entropy-content` able to see base64-encoded payloads in a script/text file (§5.2, #36). The rule's script/text path only scored whole-content Shannon entropy, but base64's 64-symbol alphabet caps that figure at 6.0 bits/byte — below the 7.0 threshold — so a base64-encoded payload could never fire regardless of what it decoded to, contradicting the module's own claim to flag "base64/packed" payloads; only raw binary appended to a script was actually caught. `HighEntropyRule::eval_embedded_payload` now falls through, when the whole-content check doesn't fire, to `eval_base64_payload`: it finds maximal runs of the base64 alphabet, decodes a qualifying one with a small bounded hand-written decoder (`nav_core::base64::decode_bounded`, shared with `plist`'s `<data>` reader — no new dependency, no panics), and scores the decoded bytes' entropy once decoded length clears `MIN_DECODED_BYTES` (768). Every candidate is examined, each bounded only by its own length — content is already capped at 8 MiB (§3), so there's no separate work cap for a payload to hide behind decoys. Run-finding treats `=` as a run byte only when it's genuine trailing padding — a `=` followed by more alphabet bytes (an unquoted `P=<payload>` shell assignment, the most common dropper shape) ends the run there instead of being read as malformed padding that silently decodes to nothing.

The base64 finding scores **8** (`BASE64_PAYLOAD_WEIGHT`), not the whole-content/`__TEXT` weight of 15 — corroboration-only per §5.1, since a script embedding a compressed/encoded payload as base64 is common in benign software (installers, bundlers) and must not alone reach Notify. A multi-line run is split into candidate *blocks* (`next_base64_segment`): consecutive lines merge into one block if they either share one exact width of at least 16 characters (`MIN_WRAPPED_LINE_LEN`, e.g. `base64 -b 32`) or are all individually at least 48 characters wide regardless of exact match (`MIN_FREEFORM_LINE_LEN`, for wrapping that varies by a column or two — real wrapping otherwise uses 64/76-column lines), optionally followed by one shorter final line (the wrap remainder); a line that fits neither is its own single-line candidate (`MIN_BASE64_RUN` = 1024 alphabet characters to qualify). This closes a false-positive class an initial real-corpus run surfaced — a one-word-per-line wordlist/dictionary (every character coincidentally in the base64 alphabet, lines joined across `\n` since a line break inside a run doesn't end it) fusing into one fake giant run that happened to decode to entropy over the threshold — **without** reintroducing the false negative a first (all-or-nothing "is the whole run uniform") version of this check had: judging the *entire* run's uniformity at once meant one unrelated short line anywhere in it — a blank MIME separator right before a real payload, a heredoc terminator word right after one — disqualified the genuine payload along with the wordlist, an evasion vector (a single blank line in front of a payload would have blinded the detector). Splitting into independently-delimited blocks fixes both directions at once: a block stands on its own regardless of what's adjacent to it. Base64 of plain text still decodes to low entropy and is deliberately not scored by this rule — that shape is `suspicious-strings`/issue #35's territory.

A run is skipped as an ordinary data-URI/PEM carrier only once a candidate's *decoded* bytes actually back up what the text before the run claims — a data URI's decoded bytes must start with its mime's known magic (png/jpeg/gif/webp/woff/woff2/pdf/zip/gzip); PEM/PGP armor must decode to a DER SEQUENCE, an OpenPGP packet tag, or carry a `Proc-Type: 4,ENCRYPTED` header (ciphertext, no magic to check). A bare `;base64,` or `-----BEGIN X-----` in front of an unrelated payload no longer suppresses it. The carrier is decided once per run — from the first candidate segment long enough to decode meaningfully — and applied to every segment in it, not just the one nearest the claim text, so a run re-wrapped into multiple blocks doesn't leak past its first block; `-----BEGIN ` is found by looking back up to 8 header (`Key: value`) or blank lines, so a PGP block's `Version:`/`Comment:` headers or a legacy key's `Proc-Type:`/`DEK-Info:` no longer defeat detection.

Same rule id; fixtures: `suspicious/dropper_base64_packed.sh`, `dropper_base64_unquoted_assign.sh`, `dropper_base64_narrow_wrap.sh`, `dropper_spoofed_data_uri.sh`, and benign `inline_image_data_uri.js`/`pem_bundle.sh` (regenerated to carry real PNG/DER magic in their decoded bytes, now that the skip validates content). A real-corpus comparison (Homebrew Cellar, `~/.cargo/bin`, `/usr/bin`, installed `.app`s — 161,215 files) against the prior release found **zero files with a changed recommendation** (568 `notify` / 0 `high-risk` on both builds) and 9 files newly carrying a `high-entropy-content` signal, all staying `no-action` at score 8: seven `embedded.provisionprofile` files (an X.509 certificate is legitimately base64 inside the plist's `<data>` element — not caught by the data-URI/PEM skips, since Apple's plist format uses neither) plus a GarageBand wavetable plist and a bundled JS asset. The wordlist/dictionary false positives an earlier version of this change hit (`nmap`'s `passwords.lst`, two `wine-gecko` `en-US.dic` arch variants, ProtonVPN's `ignis_10k.txt`) no longer fire, as intended; two other files that same earlier version had stopped detecting as a side effect (Python's `test_email` fixtures, Perl's `tkpp`) fire correctly again under the block segmentation, confirmed individually. Since at weight 8 a file's recommendation can only change if its prior (main) score sat in `[7, 14]` (or `[37, 44]` with a second category), the full-corpus re-scan was replaced by a targeted one for this revision, repeated after the review-round fixes above with the same result: zero recommendation or score changes, and the 13 files known to carry the base64 signal all stay `no-action`. The `<data>`-tag carve-out remains unimplemented, reported for a follow-up to judge rather than tuned around. No architecture/phase/scope change — Phase 0a scanner work per §12.

**Changelog from v0.37 (2026-09-26):** Closed the `macho-loader-anomaly` gap in #39: its writable/transient-location list (§5.2) was missing per-user `$TMPDIR` (`/var/folders/`, `/private/var/folders/`), even though the `launchd-persistence-plist` rule already flagged the same locations — a dylib/rpath load from `$TMPDIR` went unscored. The prefix list is now a single private `TRANSIENT_PREFIXES` const in `rules::mod`, used by both rules, so they can't drift apart again; `is_writable_or_transient` picks up the two new prefixes as a result. New fixture `suspicious/macho_tmpdir_dylib` (unsigned, dylib load from `/private/var/folders/…/T/libupdate.dylib`); golden snapshot gains that one entry. No other scoring change.

Also (#37): fixed `ENTITLEMENT_WEIGHT_UNSIGNED` being unreachable dead code — entitlements are only ever extracted from inside an `LC_CODE_SIGNATURE`, which already sets `has_code_signature = true`, so the `!has_code_signature` branch could never run. The intended distinction (README's "suspicious entitlements on unsigned binaries") was really ad-hoc-vs-identity, which the parser couldn't previously see. `MachOImage` gains `code_directory_flags: Option<u32>`, the bitwise OR of `flags` across every CodeDirectory found (slot 0 and the alternate range `0x1000`–`0x1004`, cs_blobs.h — XNU accepts a binary's only CodeDirectory there too) in the same bounded SuperBlob walk that recovers entitlements (`extract_entitlements` became `extract_signature_facts`, returning both). `macho-loader-anomaly` now weights a suspicious entitlement at `ENTITLEMENT_WEIGHT_ADHOC` (18) when the CodeDirectory's flags carry `CS_ADHOC` (`0x2`, `<Security/CSCommon.h>`), else `ENTITLEMENT_WEIGHT_SIGNED` (10) — including when the flags are unknown, so an unrecoverable CodeDirectory doesn't assume the worse case. New fixture `suspicious/macho_adhoc_disable_lib_validation` (ad-hoc CD flags, `disable-library-validation`, benign system dylibs only); golden snapshot gains that one entry. §5.2 updated to describe the ad-hoc-vs-identity weighting.

Follow-up to #37, found via a real Xcode "Sign to Run Locally" Debug build: that ad-hoc-vs-identity weighting made `com.apple.security.get-task-allow` score 10 on *every* ad-hoc binary requesting it, but Xcode adds get-task-allow to every Debug build and every Debug build is ad-hoc signed — so it was flagging the ordinary dev-build state, not an anomaly (verified false positive: a Debug build with app-sandbox + get-task-allow + network entitlements went from Notify (17) on main to 25 on this branch). `get-task-allow` is now scored on its own policy (`EntitlementPolicy::IdentityOnly` next to the other three's `WeightedByIdentity`): it contributes `ENTITLEMENT_WEIGHT_SIGNED` (10) only when the CodeDirectory confirms a real, non-ad-hoc identity, and contributes nothing (not even named in the finding) when the binary is ad-hoc or the CodeDirectory is unrecoverable — notarization rejects get-task-allow on a real identity, so it stays meaningful there. New fixture `benign/macho_adhoc_debug_get_task_allow` (ad-hoc CD flags, app-sandbox + get-task-allow, benign system dylibs); golden snapshot gains that one entry, with no `macho-loader-anomaly`.

Doc-only, no code change: further tightened §5.2's `macho-loader-anomaly` paragraph after PR #47 review — fixed a broken sentence left by an earlier edit (a stray mid-sentence period before "and a handful of..."), replaced the stale "the rule iterates `macho::parse_all`" wording with the actual `parse_all_slices`/`NotApplicable`-degrades-to-`Partial` behavior (§11.8, #38), and spelled out that a `0xCAFEBABE` file only counts as a fat Mach-O when some arch entry points at a real thin Mach-O header — deliberately not an arch-count cap (#46).

More PR #47 review fixes, no version bump: a fat table can declare up to `MAX_FAT_ARCHES` (1024) entries pointing at the same slice offset, and each parsed slice owns up to 256 KiB of entitlements — `parse_fat_all` now walks each *distinct* offset once (a duplicate of a walkable slice isn't re-walked or counted as skipped), and `parse` returns the first walkable slice via `find_map` instead of building every slice just to take the first (Refs #37). A second `LC_CODE_SIGNATURE` in one slice has no legitimate meaning or documented kernel precedence — rather than let it silently overwrite the first's entitlements/CodeDirectory facts, `parse_thin` now rejects the whole slice as malformed; new fixture `suspicious/macho_duplicate_code_signature`, golden snapshot gains that one entry with `completeness: partial` (Refs #37). Also, `macho-loader-anomaly` pushed one entitlement finding per fat slice, so a universal binary carrying the same anomaly in every slice scored and repeated it once per slice; suspicious entitlement keys are now unioned across slices like `bad_paths` already was, each key weighted once by the worst (most ad-hoc) slice that requests it — no fixture changed (Refs #37).

Also (#37): the `CS_ADHOC` bit is self-declared by the signer, so trusting its absence alone let a crafted CodeDirectory claim "real identity" it never had. Verified on real binaries: an identity signature (Developer ID/Apple) wraps a non-empty CMS blob (`CSSLOT_SIGNATURESLOT`/`CSMAGIC_BLOBWRAPPER`, length > 8); a hand ad-hoc signature has that wrapper but empty (length 8); a linker signature has none. `MachOImage` gains `has_cms_signature: bool`, set in the same bounded SuperBlob walk; a slice now counts as ad-hoc when any CodeDirectory has `CS_ADHOC` set **or** (a CodeDirectory was read and) there's no non-empty CMS blob — "unknown" is unchanged, still only when no CodeDirectory could be read at all. New fixture `suspicious/macho_identity_claim_without_cms` (CD flags=0, no CMS blob); golden snapshot gains that one entry. Real-binary sanity (`/bin/ls`, CrossOver.app, a Debug `tiny_hello_arm64`, the NetTools.app Debug build named above) scored identically before and after.

**Changelog from v0.33:** Fixed `is_disabled` silently misreporting the boolean form of `launchctl print-disabled` output (§11.10/§11.8). New `nav-service` unit tests pin the parser's word/boolean forms, the absent-label and substring-collision cases, and that clean/is_clean still hold across a preloaded uninstall. No scanner/scoring change; golden snapshot unchanged. Phase 0b Stage A work per §12.

**Changelog from v0.12:** `.pkg`/xar container parsing landed, closing §12's "biggest untouched parser surface" for Phase 0a. A `.app` bundle is scanned as one unit: every member is traversed regardless of `--recursive` (a bundle is inherently nested, and trojanized `.app`s hide payloads in `Contents/Resources/` or helper tools, not just the main binary), the main executable is resolved by the `Contents/MacOS/<name>` convention (authoritative `Info.plist`/`CFBundleExecutable` parsing is a tracked follow-up — real bundles ship binary plists, needing the §11.9 parser discipline), and a narrow fixed set of compiled resources (`Info.plist`, `PkgInfo`, `_CodeSignature/`, `.nib`/`.car`/`.strings`/`.lproj`/…) is traversed but not scored, to limit false-positive surface (§1). A directory/bundle verdict is the worst single member's — per-file scores are never summed. `rules test` gains `--recursive` to mirror `scan`. The shared walker also sorts output (§11.1) and no longer follows directory symlinks. New benign `SampleHelper.app` fixture pins this in the FP harness, which now also walks `.app` directory fixtures. No architecture/phase/scope change — Phase 0a scanner work per §12.

**Changelog from v0.8:** Implemented Phase 0a's Mach-O `__TEXT` entropy heuristic (§5.2). `nav-core` now carries a small, bounded, dependency-free Mach-O parser (thin and fat/universal) that locates the `__TEXT,__text` section, and the entropy rule scores *structurally* rather than whole-file: high entropy is a suspicion signal only inside a Mach-O `__TEXT` section (packed/obfuscated code) or embedded in a script/text file (obfuscated/base64 payload).
