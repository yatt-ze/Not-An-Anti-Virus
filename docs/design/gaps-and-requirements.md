## 10. Explicitly Out of Scope / Known Gaps

- **No auth-time execution blocking** — by design, not a limitation to fix.
- **No process-injection/code-injection detection** (`mmap`-into-other-process, `task_for_pid`, `ptrace` tampering) — main capability gap versus ESF. Acceptable given threat-model focus (commodity malware + infostealers, not APT-grade).
- **Process exec/fork attribution is best-effort, not comprehensive.** Without ESF or BSM (both excluded, see §4), short-lived processes between polling intervals and non-GUI process chains are not reliably observed. This is the most significant honesty requirement in the whole document — do not let CLI output, documentation, or scoring confidence imply stronger process-tree visibility than actually exists.
- **TCC/permission-probing detection is not implemented in v1** — no current event source observes it; listed as experimental/future only.
- **NAV's own static-analysis coverage may be degraded by Full Disk Access requirements.** TCC restricts access to protected user-data locations (Desktop, Documents, Downloads, Mail, and parts of `~/Library`) regardless of privilege level — root does not bypass this. `navd` opening files under these paths for Mach-O/string/entropy analysis likely needs Full Disk Access granted explicitly via System Settings. FDA is the one TCC scope with no consent-prompt mechanism at all — it can only be added manually via the FDA pane, which is actually the more viable path for a headless daemon than Files & Folders-style prompts (those require a UI session TCC can attribute to a requesting app, which `navd` doesn't have). Never triggered automatically: `navctl setup fda` is a separate, explicitly user-invoked command (opens the correct System Settings pane and reveals the `navd` binary in Finder to speed up the manual add) — it is not run as a side effect of `navctl service install` or any other command the user didn't ask for, consistent with the non-invasive philosophy in §1.

  **Known active platform risk, not just a theoretical edge case:** as of macOS Tahoe 26.1/26.2 beta, there are confirmed, ongoing reports (Trellix, engaged directly by Apple DTS) of CLI/daemon binaries failing to appear in the FDA list at all after being added via drag-and-drop — a bug affecting exactly the mechanism `navctl setup fda` depends on, currently unresolved. This isn't hypothetical: it's happening to comparable tools right now. Phase 0b (§12) must track this rather than assume the manual-grant UX works as designed on every macOS version.

  **The check itself must not overclaim certainty.** There is no general supported API to determine whether FDA has been granted — Apple's own guidance is to spot-check the actual paths the product needs, using operations as close as possible to real usage, since even a failed read doesn't uniquely mean "FDA absent" (it could equally mean the path doesn't exist, an ACL denied it, the file was transiently unavailable, or the probe itself stopped being representative on a given macOS version). Accordingly, `navd` runs **a small matrix of per-area probes**, not a single canary, and reports each independently rather than collapsing to one boolean:

  ```rust
  enum ProtectedCoverageArea { Downloads, Desktop, Documents, BrowserProfiles, MailData, UserApplicationSupport }
  enum CoverageProbeResult { Accessible, Denied, Missing, Inconclusive, NotTested }
  ```

  `navctl status` reports per-area results (e.g. `Downloads: verified`, `Documents: degraded`, `Mail data: not tested`), not a single `Full Disk Access: granted/not granted` line — that single-boolean framing implies more certainty than any probe can actually establish. Probes read minimal metadata only; they don't retain user content. This state is re-checked periodically, not just at startup, since grants can be revoked at any time, and (see §11.10) may need re-verification after a binary update changes signing identity. **A file that can't be read is not silently skipped — it's reported as explicitly unscanned**, so the gap is visible per-event rather than only discoverable in aggregate:
  ```
  14:32:01  NEW FILE  ~/Downloads/installer.pkg  [NOT SCANNED: Full Disk Access not granted]
  ```
  Worst case without a grant: exactly the directories malware most commonly lands in (Downloads, Desktop) get visibly-flagged-as-unscanned static-analysis coverage, not silently weaker coverage. `navctl rules test` (on-demand, user-invoked from an interactive Terminal session) may have meaningfully different TCC exposure than `navd`'s automatic background scanning — an interactive process has a real UI attribution chain a Files & Folders prompt can attach to, or may inherit whatever the invoking terminal has already been granted — so on-demand scanning of a specific file could plausibly work even for a user who never grants `navd` FDA at all. This distinction is unconfirmed and is a Phase 0b feasibility question (§12), not a Phase 3 polish item, alongside whether the grant is system-wide (tied to `navd`'s code identity) or needs repeating per logged-in user.
- **Network hostname visibility is opportunistic, with named gaps**: NAV parses plaintext SNI from TLS ClientHellos it successfully captures and reconstructs. It does not recover the hostname for QUIC/HTTP3, for non-TLS protocols, for direct-IP connections, or for **ECH-protected connections** — Encrypted Client Hello (RFC 9849, standardized March 2026) encrypts the ClientHello, including SNI, even over otherwise-standard TLS 1.3, and adoption is expected to grow. This is a meaningfully different gap from QUIC — it affects traffic that would otherwise look like ordinary parseable TLS.
- **Fileless techniques** (memory-only payloads, `eval`'d scripts never written to disk) are not covered — rarer on macOS, explicitly out of v1 scope.
- **Daemon self-defense** is minimal by design choice — no kernel-level tamper resistance. Bare minimum: detect and surface unexpected daemon termination to the user on next launch (`launchd KeepAlive` + notification), not full anti-tamper hardening. **This is a conscious tradeoff worth stating plainly given the stated threat model**: Atomic-Stealer-class infostealers (§1's named primary threat) commonly include basic AV/EDR discovery and kill-attempts as standard tradecraft, so a motivated sample may detect and terminate `navd`. v1 accepts this and relies on the after-the-fact termination alert rather than resisting it — full anti-tamper hardening is a Phase 4+ question, not a v1 gap being overlooked.
- **Static packer detection is heuristic and evadable** (§5.2, #67). `high-entropy-content` flags a packed `__text`, a high-entropy region inside it, and payload-shaped regions elsewhere (a writable+executable or non-standard segment, or a section much larger than `__text`). A payload in a standard data segment beside a normal-sized `__text`, one in segment slack outside any section, one appended past the last segment, one whose padding is spread evenly through it, or one under 96 KiB placed across the 32 KiB window grid (only a 96 KiB run is sure to fill a 64 KiB window) scores nothing or only corroboration, because benign binaries carry the same entropy in the same places. Unpacking at runtime needs writable executable memory, which is Phase 2 behavioral territory, not static analysis. No entitlement check closes this either (#68): on Apple Silicon (macOS 27), a binary without the hardened runtime can generate and run code through `MAP_JIT` or `mprotect` with no entitlement at all. Only a hardened binary needs `com.apple.security.cs.allow-jit` (`MAP_JIT` only) or `...allow-unsigned-executable-memory` (both paths). In a 4,554-file Mach-O corpus every one of the 59 hardened binaries carrying either key verifies to an Apple anchor (ZAP's bundled JRE, VLC, CrossOver, Zed, iMovie, GarageBand), the case §5.2 already treats as corroboration-only, while ad-hoc or unsigned malware has no reason to opt into the hardened runtime. `macho-loader-anomaly` therefore does not score these two keys.
- **Installer JavaScript detection is textual and evadable** (§5.2, #42). The `Distribution` JavaScript is scanned as text, not executed or parsed as JavaScript. The interpreter marker only sees a string literal as the first argument of a direct `system.run`/`system.runOnce` call, so string concatenation, a variable, an alias of `system.run`, bracket access (`system["run"]`) or a JavaScript escape inside the literal is not marked, and the content rules can be evaded the same way they can in any script. Tools outside the marker's list (`open`, for one, which legitimate installers plausibly call) are not marked. External scripts that a Distribution runs from beside the package on disk (`allow-external-scripts`) are not part of the archive and are not read. The extraction follows XML rules as NAV implements them, not Installer's actual parser; a document it cannot read faithfully (a DTD entity, an unsupported encoding, xz compression, a compressed entry with nothing decodable, a zlib or gzip entry cut short until #75) is reported as not checked, so an attacker can choose `Partial` over a finding.
- **Containers other than ZIP are not opened** (§6.2, #86). A disk image (UDIF, encrypted, sparse, or a raw GPT/APFS/HFS+/ISO 9660 image) is reported as not inspected (`Partial`), never clean. A ZIP-format file is read in memory (§6.2) and is `Partial` only where something in it could not be read (encryption, an unsupported method, a limit, a disagreement between its two views, a signed Mach-O member), or when it is over the 8 MiB read limit; a real file under `X.app/Contents/` is neither flagged nor read. A `.tar.gz`, `.bz2`, `.xz`, `.7z` or `.rar` is still scanned as one opaque file and can report `Complete` with nothing found, as can a raw image with only an MBR partition map. A `.sparsebundle` is a directory; its band files are scanned like any other, and only the first band carries a partition map. In a package's `Scripts` archive, a disk image, a package or a ZIP not read in full makes the package `Partial`, but only in the first gzip member Installer extracts (#109); all the ZIPs in one package share one read budget, and past it a ZIP is unread, so `Partial`. Only the xar structure of a `.pkg` is read (§6.1).
- Naming/positioning should avoid overclaiming — "heuristic behavioral monitor" framing, not "virus protection," given the above gaps.

## 11. Cross-Cutting Requirements (Not Yet Designed In Detail)

### 11.1 False-Positive Evaluation Harness

Now targeted for Phase 0a, not Phase 1 (see §12). Start small (e.g., ~20 known-benign fixtures, ~10 synthetic suspicious fixtures, a malformed/fuzzed-input corpus) and expand continuously, rather than waiting for a large corpus before starting. Track more than pass/fail: final score, matched rule IDs, runtime, memory, files traversed. A rule change should fail CI if it pushes a known-benign sample over the alert threshold, introduces an unexpectedly high-severity signal, or produces nondeterministic output.

**Quantitative acceptance gate (NAV-015).** "Low false-positive rate is the primary success metric" (§1, §12 go/no-go) is enforced as a measured, asserted number, not left as a stated priority: the harness computes and reports the corpus's benign false-positive rate, suspicious signal coverage, verdict mix (high-risk/notify counts), partial/indeterminate count, and per-fixture runtime p50/p95, and asserts two corpus-size-independent criteria — benign false-positive rate is exactly 0%, and suspicious signal coverage is 100% (no deliberately-suspicious fixture scored silently clean). Runtime percentiles are reported but not asserted (environment-dependent, would flake CI). Peak memory stays deliberately untracked: cargo runs every test as a thread in one shared process with one allocator, so a per-fixture number would misattribute concurrent allocation — an honestly-absent metric beats a wrong one, and an honest external benchmark is the right home for it later.

### 11.1a Real-World Malware Benchmark

The fixtures in §11.1 are small and synthetic, built to exercise one rule each. This benchmark measures how the engine does on real macOS malware. It is optional and run by maintainers only: contributing never needs it, and `cargo test` must never depend on its sample store.

**Gate: regressions only.** Each sample records an `expected` result: its recommendation and completeness from the last accepted baseline. A run compares the branch with `origin/main` and fails (exit 2, as `cargo xtask corpus compare` does) when any sample's recommendation or completeness gets worse, or a sample is missing or fails its hash check. Exit 1 means the tool itself failed. Improvements are reported, and `expected` is raised on purpose in the PR that earns it. There is no absolute recall target. Chasing one would push towards family-specific rules, and NAV's detection is heuristic, not a signature feed (§5.6).

**Source and manifest.** Samples come from the Objective-See macOS Malware Collection (`github.com/objective-see/Malware`, GPL-3.0), pinned to one commit. Samples are never committed. The committed manifest, `crates/nav-core/fixtures/real-world/manifest.toml`, opens with a `[source]` table (the collection's `repo`, the pinned `commit`, and the archives' published `password`), then lists for each sample:
- `id` and `family`;
- `category`: `stealer`, `adware`, `trojanized`, `other`, `format-gap` or `apt`;
- `scope`: `in`, or `out` for nation-state (APT) samples (`apt` is always `out`, every other category `in`);
- the family `archive` and its `archive_sha256`;
- the `member` path inside the archive, and its `kind` (`macho`, `app`, `dmg`, `pkg`, `script`, ...);
- the member's `sha256`, or for an `.app` or other bundle a `tree_sha256`: the SHA-256 of one `/<relative path><TAB><sha256 hex><LF>` line per regular file in it (symlinks skipped), sorted by bytes and joined;
- `bytes`, the sample's size;
- `expected`.

The local store under that directory, `store/<id>/<member's file name>`, is git-ignored.

**Composition.** 100 samples: 33 stealers, 22 adware or scareware, 15 trojanized installers, and 10 others (miners, ransomware, commercial spyware). There are also 14 APT samples as out-of-scope controls: they are measured and reported separately, never counted as misses (§1: APT-grade threats are not the focus). Six `format-gap` samples are in formats NAV cannot read yet (Java archives, Python, Ruby, AppleScript, tar). They are expected to come out not inspected, and track progress as readers are added. Most families give one sample each, so the set favours breadth over depth.

**Isolation.** Samples are fetched and scanned only inside a throwaway macOS VM, never on the host. A golden Tart image (Virtualization.framework) holds the toolchain and a cache of the family archives the manifest needs, at `~/nav-bench-cache/<commit>/`. The archives are cached as published: still encrypted with the collection's password and never extracted in the golden image. So the only sample bytes on the host sit encrypted inside the VM's disk file. Each run clones the golden image and checks out the branch. It then takes each archive from the cache, verifies it against `archive_sha256` (re-downloading it if it is missing or does not match), and extracts and verifies the members. Finally it runs the comparison, copies the report out and deletes the clone. The cache only saves the download, about 830 MB for the 92 archives. The tool works without it, and a new pinned commit needs a cache refresh. The golden image is never pushed to a registry, since that would distribute malware. Nothing is ever executed: the scan is static.

**Tooling.** `cargo xtask malware fetch` takes each archive from the cache, or downloads it from the pinned commit, checks `archive_sha256`, extracts it with `unzip`, and places each member in the store once its hash and `bytes` match. It refuses to run unless macOS reports a hypervisor (`kern.hv_vmm_present`), with no override, so the host can never be used by mistake. `cargo xtask malware verify` re-hashes the store without network access. Both exit 0 when every sample checks out, 2 when one is missing or does not match, and 1 when the tool itself fails. Their tests use a small harmless archive built at test time, never a sample.

`cargo xtask malware scan` re-verifies the selected samples, then runs one navctl, recursively, over each sample that passed (`store/<id>/<member's file name>`); a sample that fails verification is not scanned and fails the gate, and so does one whose navctl run fails. `malware diff <base.jsonl> <new.jsonl>` compares two scans, and `malware compare` builds base (`--base`, default `origin/main`) and new navctl into one shared target directory, one after the other, scans with both and diffs, writing `base.jsonl`, `new.jsonl` and `report.txt`. Before the measured scans it runs one throwaway pass with the base navctl (`warmup.jsonl`, not compared): `codesign`'s revocation answer depends on its cache, and without the warm-up a revoked binary read `Complete` in the first (cold) run and `Partial` in the second (#150). `scan` and `compare` refuse to run outside the VM; `diff` reads files only. They reuse the corpus tool's chunk runner, JSONL reader and labels. `diff` must be given the store path the scan used (`--store`), or it stops with a tool error rather than drop every result. Paths are matched to samples by whole path component, so an id that is a prefix of another never claims its files.

Each sample's result is the strongest recommendation and the worst completeness over every file under its directory (an `.app` has many). The report has three sections: in scope, format gap, and apt. Each shows counts by recommendation and completeness for base and new, then the per-sample changes. For this benchmark a lower recommendation is a lost detection, so "worse" is the opposite direction from the benign corpus; completeness gets worse as it moves from complete towards indeterminate. The gate exits 2 when any sample is missing from new, failed verification or its navctl run, covers fewer files than in base, or has completeness worse than base, and when the recommendation is worse than base for a `scope = in` sample. For an apt sample a worse recommendation is reported but does not gate. It also fails when the base scan covers no sample. A non-empty `expected` (`<recommendation>/<completeness>`, such as `notify/partial`) is a ratchet: a new result worse than it fails by the same rules, and a better one prints `raise expected: <id> <old> -> <new>` without failing. An empty `expected` is not checked. The store lives in the VM's own clone of the repository; a working tree shared in from the host would put samples on the host disk.

`cargo xtask malware vm` is the one command that runs on the host, and it drives a whole run. It resolves `--branch` (default `HEAD`) and `--base` (default `origin/main`) to commits and packs both into a `git bundle`. Only committed code is sent, so uncommitted changes are left out. It then clones the golden image under a fresh `nav-bench-run-<unix-seconds>` name, boots it headless and waits for the guest agent. It pipes the bundle in, and with `--manifest` a manifest file from the host. Inside the clone it checks out the branch, runs `fetch` and then `compare` against the base commit, and copies `report.txt`, `base.jsonl` and `new.jsonl` back to `target/xtask-malware-vm/<unix-seconds>/`. These are text results, never sample bytes. Last, it stops and deletes the clone (`--keep` leaves it in place). Code reaches the VM only as the bundle, so a branch needs no push and the VM needs no GitHub access. All user input reaches the guest as arguments, never as script text. An interrupted run can leave a clone behind, so each run lists stale `nav-bench-run-*` VMs but never deletes them. The exit code is compare's: 0, 2 for a gate failure, and 1 for any other failure, in the guest or on the host. `fetch` exiting 2 does not stop the run, because `compare` re-verifies the store and reports the missing samples.

**Known gaps.** The collection has no Adload, the most common macOS adware family. Only 22 of its ~380 Mach-O files are arm64-only, so the benchmark leans heavily on x86_64 and universal code. Some member names contain CR or newline characters, so tooling must treat paths as opaque bytes.

### 11.2 Ruleset Rollback

`navctl rules rollback`, since there's no cloud-based auto-tuning safety net; a bad rule update needs a fast, user-triggerable reversion path.

### 11.3 Resource/Energy Budget

Explicit internal target (e.g., <1% average CPU, low Energy Impact rating in Activity Monitor), tested against, not assumed. `navctl status --resource-usage` should self-report honestly.

### 11.4 Event Log Privacy

Local SQLite log contains file paths, process args (redacted by default, see §4.2's `Sensitive<T>`), possibly hostnames. Needs encryption-at-rest consideration, retention/rotation policy, and access controls so another local user can't read root's log without permission.

### 11.5 Clean Uninstall

`navctl uninstall` must fully remove the LaunchDaemon, the `navnotify` LaunchAgent (§9.2), and all local data with no orphaned processes/files. No System Extension to clean up given the packet-capture approach (§4.1), which simplifies this considerably versus a Network-Extension-based design.

### 11.6 Decompression-Bomb Guardrails

Numerically specified in §6.2 (depth/size/count/time/ratio limits, all user-configurable). Remaining work is implementation, empirical validation of the defaults against real-world large-but-legitimate archives, and override UX.

### 11.7 File-Race (TOCTOU) Handling

A path referenced by an event may be replaced before it's scanned. Scan through an opened file descriptor, capture device+inode identity, and detect/record if the underlying file changed between observation and scan.

**Implemented for the path-based external checks (NAV-003, gate P0.3, from #5).** `ScanContext::load` captures an `ObjectIdentity` (dev, inode, size, mtime) by `fstat`-ing the *opened* file handle and reads the bytes through that same handle, so the identity describes the object whose bytes were actually scanned rather than a separate pre-open `stat` that a swap in the open→read gap could desynchronize from the read. Every path-based external check then re-stats the path after running and drops the tool's result if that identity changed — the tool would have inspected a different object than the one this scan scored, so its verdict is treated as inconclusive (`None` → the signing rules already fold that into `NotApplicable`), never as clean. This covers all three tools uniformly: `codesign -dv` and `spctl` through their memoized `ScanContext` accessors, and `codesign --verify` (revocation) through the un-memoized `run_object_bound` wrapper over the same guard, so no signing rule reaches disk by a path the guard doesn't cover.

**Files are opened without following a symlink below the target (#239, threat-model E1).** The target the user named is resolved once (symlinks followed: that is the user's intent) and held open as a directory. Every file under it is opened by an `openat` walk from that descriptor: each directory component `O_NOFOLLOW | O_DIRECTORY`, the file itself `O_NOFOLLOW | O_NONBLOCK | O_NOCTTY`, then `fstat` must show a regular file. A single-file target is resolved the same way and its leaf opened beneath its parent. So a file, or a parent directory, swapped to a symlink after the walk listed it fails to open, and the file is reported unreadable, a coverage gap, never clean (§11.8). It is not read through the link. Later steps describe the opened object: the quarantine xattr is read through the held handle, the `.app`-bundle exemption (§6.2) judges the canonical root joined with the symlink-free relative path, and bundle `Info.plist` and signature-manifest reads use the same walk. The post-tool identity re-check above re-opens through the same walk and `fstat`s the result, so a path swapped to a symlink, even one back to the same file, drops the tool's result. The walk is safe Rust (`rustix`); `nav-core` keeps `forbid(unsafe_code)`. The root descriptor is the seam the daemon can later hand in from a broker (threat model §7).

This deliberately *narrows*, not closes, the window, and must not be presented as a complete TOCTOU guarantee. What remains: `codesign` and `spctl` still run by path, and the re-check runs after them, so a swap reverted before the re-check, or a same-size, same-mtime swap into a reused inode, goes unseen. The directory listing still reads by path, so a parent swapped before it is listed exposes the outside directory's entry *names* (as paths that then fail to open), never contents. A hard link to a file outside the target is a regular file inside it and is scanned (threat model R2, out of scope here). The full close — binding a cryptographic digest of the scanned bytes into the reported result (JSON provenance), and an unprivileged worker handed descriptors by a broker — remains for when the privileged daemon acts on verdicts (Phase 0b+), where a wrong-object trust decision becomes a security boundary, not only a correctness bug.

### 11.8 Loss/Degradation Reporting

Every source should be able to report `Lossless / Dropped{estimated} / Coalesced / ResyncRequired` rather than silently dropping events. A monitor that silently loses visibility is worse than one that honestly reports degraded coverage.

### 11.9 Packet-Capture Data Minimization

Captured payload bytes are attacker-controlled input, same category of risk as Mach-O/xar parsing (§3), and also a privacy concern beyond what §11.4 already covers (paths/args/hostnames) — raw packets can contain far more: credentials, internal IPs, arbitrary cleartext payload. Bounded reassembly only, never persisted by default:
```rust
struct CaptureLimits {
    max_bytes_per_flow: usize,
    max_reassembly_flows: usize,
    max_reassembly_bytes_total: usize,
    flow_idle_timeout: Duration,
    handshake_timeout: Duration,
}
```
For SNI parsing specifically: retain only the minimum bytes needed for a bounded ClientHello reconstruction, then release the buffer. The packet parser needs the same fuzzing discipline as the Mach-O/xar parsers (malformed link-layer types, IP fragmentation, TCP option edge cases, deliberately oversized advertised lengths, overlapping retransmissions).

### 11.10 Safe Root-Daemon Installation Path (Homebrew-Specific)

`brew services start` conventionally targets a user-level `launchd` service; `navd` needs a genuine system-level LaunchDaemon (root, BPF access, cross-user file/process visibility). More importantly, a LaunchDaemon plist must **never** point directly at a binary living in the Homebrew Cellar, since that path is writable by the Homebrew-owning user — if an unprivileged user can replace the daemon binary, the next `navd` restart runs their code as root. Split installation:
- `brew install nav` installs `navctl` (unprivileged CLI) normally. The install script (§13) puts it in a user-writable directory too, so the same rule holds there.
- `sudo navctl service install` is a separate, explicit privileged step that copies the `navd` binary to a root-owned location (e.g. `/Library/PrivilegedHelperTools/`), creates `/etc/navd`, `/private/var/db/navd`, and the scratch/quarantine directories with correct ownership, writes a `/Library/LaunchDaemons/...plist` pointing at the *copied*, root-owned binary (not the Cellar path), and bootstraps the system `launchd` service.
- `navctl service uninstall` reverses this and doesn't touch/change ownership of the Homebrew-managed CLI install.
- `/Library/PrivilegedHelperTools` is Apple-shared, so install creates it only if absent, writing a `helper-dir-created` marker in `/private/var/db/navd` first. Uninstall (and the residue check) treat the dir as ours only when that marker is present and the dir is empty: a dir that pre-existed, or that holds another installer's helper, is left alone. The helper dir is reclaimed before the state dir, and the state dir is kept if that fails, so a partial uninstall leaves the marker for the residue check to report and a re-run to finish.

This preserves Homebrew as the primary discovery/install path (§13) while giving the privileged component its own, more defensible installation story — worth treating as its own small threat model rather than an afterthought. **This also plausibly helps the Full Disk Access grant from §10, though this must be tested, not assumed**: TCC's "responsible code" determination is not fully documented by Apple and can change across macOS versions. A stable path and a stable code requirement are *expected* to improve grant continuity across `navd` upgrades. NAV has no Developer ID (§13), so a stable requirement means a self-signed certificate; an ad-hoc identity changes every build. Grant survival is an empirical question, not a guarantee — Phase 0b should test at minimum: same version reinstalled, new version with the same identifier and certificate, a certificate renewal, and a CLI update that doesn't touch the daemon version.

`launchctl print-disabled system` reports a label's record in either word form (`=> disabled`/`=> enabled`) or boolean form (`=> true`/`=> false`) depending on macOS version; the residue check parses both. The one `=> enabled` record left by clearing a real disable override (see the v0.32 changelog entry) has no CLI to unset — it's reported by the residue check for visibility but not asserted clean, the same honest-residual treatment as the TCC grant in §11.8.

### 11.11 Ruleset/Config Integrity

A tool whose entire purpose is detecting local file tampering has an obvious blind spot if its own ruleset and config files aren't protected against the same thing — e.g. malware writing itself into `denylist`/allowlist as a bypass, or quietly degrading a rule's weight below threshold before the persistence-write heuristic even fires. Baseline requirements: the ruleset file and `/etc/navd/config.toml` are root-owned and root-write-only (`navd` reads them as root; edits go through `navctl config set`/`navctl rules reload`, which are themselves gated by the per-method socket authorization in §9.1, not direct file edits by an unprivileged process). Whether to add an integrity check on load (checksum/signature against the last-known-good state, surfaced the same way a corrupted-state warning would be) is worth deciding during Phase 3 alongside rollback (§11.2), rather than left unaddressed.

### 11.12 Whole-Target Scan Budget

The per-file read cap (§3) and per-container extraction limits (§6.2) bound the work *one* file or archive can cause, but a target that is a directory or `.app` bundle can still expand to an unbounded amount of work through sheer file count, directory depth, or aggregate size — a concern that grows in Phase 0b+ once event ingestion turns arbitrary filesystem activity into daemon workload. `scan_target` therefore enforces a `ScanBudget` (`max_files`, `max_total_bytes`, `max_depth`, `max_entries`; conservative defaults). `navctl scan` and `navctl rules test` take `--max-files` and `--max-total-bytes` to change the first two for one run, in either direction; `max_depth` and `max_entries` are fixed, and `navctl config` may later make the defaults persistent. `max_entries` bounds traversal *breadth* — the total directory entries the walk may examine — which the other three miss: a tree of pathologically many empty directories scores no files and reads no bytes, so `max_files`/`max_total_bytes` never trip and only an entry ceiling keeps the walk (and the traversal stack) bounded. Hitting any ceiling stops the scan and records a structured `BudgetOutcome::Exhausted(limits)`, the set of every ceiling hit (#105), rather than silently dropping coverage: the target is reported with incomplete coverage (`coverage_complete() == false`, surfaced in both human and `--json` output), never as a clean scan, consistent with §11.8's "a monitor that silently loses visibility is worse than one that honestly reports degraded coverage." This mirrors the §6.2 container path, where hitting a limit is `partial`/indeterminate, not automatically malicious. The budget is the target-level counterpart to those local limits, not a replacement for them. Budget exhaustion is uniform across the CLI surface: both `navctl scan` and `navctl rules test` print a partial-coverage warning and return exit code `3` unless a scanned file was itself flagged (`1`/`2`, §8), so a script can't read a truncated traversal as a clean `0`.

`max_total_bytes` counts the bytes each file's scan reads from disk itself: the 8 MiB prefix (§3) and every read past it (counted when attempted, re-reads again). Reads served from the prefix cost nothing. The file's length doesn't bound that, since rules stream past the prefix (#45): any file up to 512 MiB that is cut off at the prefix is streamed by `suspicious-strings`, and a Mach-O is streamed again by `high-entropy-content` over `__TEXT` and each payload-shaped region (which can overlap it), plus `scan_ranged`'s reads and a package's `Scripts`/`Distribution` reads (within the xar read-back budget, §6.2), so one file can cost more than its length (#53). It also counts the bytes each file's container readers decompress (#166): zip members (nested zips included), a package's TOC (once per rule that parses it, and its full ceiling when the inflate fails), its `Scripts` and `Distribution` entries and every gzip layer inside them, and zips read among `Scripts` members, whose spend is rolled up to the package file. Stored members and entries are not counted, since their bytes were already read. Without this a small file that decodes a lot cost little: a 1.7 MB zip of 256 distinct compressible 1 MB members spends its whole 256 MiB read-back budget (about 2 s) while charging the target 1.7 MB, so a directory of 1,000 such files was about 30 minutes of CPU inside a barely touched budget. Now the same 4 GiB ceiling covers reads and decoding together, and such a directory stops after 17 files (about 30 s), reported as `TotalBytes`. Decoding done by content rules on the bytes they scan (base64 runs) is bounded by the per-file prefix and is not counted. Reads by `codesign` and `spctl` are not counted. They run in their own processes, and on a bundle's main executable or a framework binary they check the whole enclosing bundle, so the file's length would not measure them (#106). After the first file, a file is started only if its length, capped at the 512 MiB streaming limit (`MAX_STREAM_BYTES`, §5.5), still fits; the first is always scanned. The length is taken from the opened file before anything is read, so a refused file is not read. Each admitted file gets a hard allowance of what is left of the ceiling (all of it for the first), held on its `ScanContext` and charged as the work happens (#104): a read past the prefix is refused before it reads, the prefix itself is cut at the allowance, and each container decode runs under a budget lowered to the allowance (a zip's read-back; a package's TOC; its `Scripts`/`Distribution` read-back first, then the zips among its members from what that leaves). The in-process reads and decodes therefore never exceed the ceiling; `codesign`/`spctl` reads are still uncounted (#106). A tool run is skipped when the allowance left at that moment, after whatever earlier rules spent, is below the file's length. A refused read or a skipped tool makes the rules depending on it `NotApplicable` or incomplete, as a failed read does (§11.8); a skipped Apple-anchor check leaves `high-entropy-content` and `macho-loader-anomaly` at their undemoted weight, marked incomplete; a package `Scripts` cut under a lowered read-back is a gap, never the starved-scripts finding. The file gets a `byte-budget` coverage gap naming `--max-total-bytes`, so it is never `Complete`, and the target records `TotalBytes`. A container gap seen under a lowered cap is attributed to the budget even if it might have happened anyway, which errs towards `Partial`. Every limit hit is reported, collection-time (`max_files`, `max_depth`, `max_entries`) and byte alike, since raising any one alone may not reach full coverage (#105). At the 4 GiB default a scan of a large app folder can hit the ceiling and report partial coverage; that's the honest outcome, and `--max-total-bytes` raises it. The budget governs *traversal*, so a directly named single-file target does not consult it — there is nothing to traverse, and no target-level ceiling applies to a single file (a rule streaming that one file up to `MAX_STREAM_BYTES` is unaffected by `max_total_bytes`, which only sums *across* files). `max_files`/`max_total_bytes`/`max_depth` apply only when a directory or `.app` bundle expands into a file set.

A budget ceiling isn't the only way traversal can come up short: a subdirectory encountered mid-walk can itself be unreadable (permission denied, a race). `collect_files` treats this the same honest way as a ceiling — the directory's path is recorded (deduped, sorted for determinism §11.1) and traversal continues past it rather than aborting the scan (#32). `TargetScan::unreadable` carries the affected paths and folds into `coverage_complete()` alongside the budget outcome, so an unreadable subtree raises an otherwise-clean target to exit `3` through the existing `for_target` completeness check with no separate code path; `navctl rules test --json` on a directory/bundle target gained an additive `unreadable` array (no schema bump at the time) and the `navctl scan --json` target summary carries the same array (#51); `navd scan-once --json` reports unreadable directories on stderr only, same as its human output. This is unlike the named target *root* itself being unreadable, which stays an operational error (exit `4`, §8) — there's no partial traversal to report when nothing was ever entered.

**External tools are bounded too (#158).** Each `codesign`/`spctl` spawn runs by absolute path (#157), is killed after 60 s and keeps at most 1 MiB of each output stream; a timeout or cut capture makes the rules depending on it `NotApplicable` (§11.8). Real runs over `/Applications` peaked at 10.3 s (Xcode, `codesign --verify --deep`). Per file the scan spawns at most six: `-dv`, the signer check and `spctl` (each cached on the scan), `--verify --deep` for revocation, and the strict anchor check, up to once each in `high-entropy-content` and `macho-loader-anomaly`. The worst-case stall is 6 x 60 s = 6 minutes a file. There is no wall-clock limit on the whole target: the byte budget bounds container decoding deterministically instead (#166).
